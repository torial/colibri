# Tuning for a 2-socket Xeon Skylake-SP workstation (Dell Precision 7820 and kin)

Written for 2x Xeon Gold 6132 (14 cores/socket, SMT on, AVX-512 F/BW/VL/DQ/CD, **no VNNI**,
no AMX), 192 GB in 12 channels of DDR4-2666, one NVMe, Alpine Linux (musl, gcc, libgomp).
Everything below was developed on a single-node cloud VM with an AVX-512-VNNI Xeon: the
kernels are bit-exactness tested there, the NUMA code is unit tested against fake sysfs
trees and `mbind` on one node, **nothing was run on a two-socket machine**. Treat the
numbers you get on the 7820 as the truth and this page as a map.

## Where the work is: `dev`, not `main`

## What the engine already does for this class of machine

| | state in `dev` |
|---|---|
| Team size = physical cores, hot OpenMP team (`OMP_PROC_BIND=close`, `OMP_PLACES=cores`) | yes, `omp_tune.h`, `colibri.c` |
| `COLI_NUMA=1`: expert slabs (and dense tensors) page-interleaved over the nodes | yes, opt-in |
| int8 dot kernels: AVX2, AVX-VNNI, AVX-512-VNNI, AMX, NEON | yes |
| AVX-512 **without** VNNI (Skylake-SP, 6132) | **fell back to AVX2 (256-bit)**: `IDOT_KERNEL "avx2"` even with `-march=native` |
| NUMA-local placement of the dense trunk | no |

## What this branch adds

1. **`avx512bw` kernel tier** (`idot.h`). `coli_dpbusd512` = `vpmaddubsw + vpmaddwd + vpaddd`,
   the value of `vpdpbusd`. Used by `dot_i8i8`, `dot_i8i8_rows`, `dot_i4i8`, the i4p
   kernels (`dot_i4p_u`, the grouped `i4p_gidot*`) and the int8 r16 trunk kernel (`i8r16_group`).
   Saturation: `vpmaddubsw` clips its int16 pair sums, so only operand ranges that cannot
   clip are routed there (`|w|<=128` unsigned x `|x|<=127`; nibbles; the r16 rows go through
   the sign trick like the AVX2 form). `tests/test_idot_extreme.c` runs the worst-case
   operands on every tier. Kernels with a biased uint8 operand up to 255 (the GGUF / rows16
   expert formats in `ggml_quants.h`, `expert_ffn.h`, `lowbit_g16.h`, `vq2_g32.h`) were
   **not** ported: they stay on their AVX2 form.
   - Also ported, same rule: the expert kernels `xf16` (`expert_ffn.h`, nibble codes <= 15; the
     block's eight `vpmaddubsw` are summed in int16 and widened once) and `xl16`
     (`lowbit_g16.h`, codes <= 78). Not portable to Skylake-SP: the GGUF kernels (`ggml_quants.h`
     needs AVX-512 VBMI, which this CPU lacks) and `vq2_g32.h` (codes up to 255 would saturate).
   - Measured here (Cascade Lake, same core as Skylake-SP; cache-resident, 1 thread): int8
     dot 1.2-2x, r16 1.4-2x, int4 about equal; DRAM-bound sizes: no change (one core does
     ~7 GB/s here whatever the instructions). So: a prefill / batch / cache-hot win, not a
     decode-from-RAM win.
   - **AVX-512 frequency licence.** On Skylake-SP heavy 512-bit integer code lowers the
     all-core clock. If `bench_idot_tiers` with the whole team (below) is slower than the AVX2
     build, add `-DCOLI_NO_AVX512BW_IDOT` (`EXTRA_CFLAGS=-DCOLI_NO_AVX512BW_IDOT`).
2. **`COLI_NUMA=2`** (`numa_topo.h`, `colibri.c`). Every decode matmul of the trunk is a
   static row split, so thread t always reads the same slice of every tensor. `COLI_NUMA=2`
   (a) builds `OMP_PLACES` from sysfs in node order (`{0,28},{2,30},...`: a core's SMT
   siblings together, node 0's cores first), so thread blocks follow nodes whatever the CPU
   numbering is (round robin or node by node), and (b) binds each dense tensor of 2 MB or
   more to the nodes in the proportion of their cores (`MPOL_BIND`, one piece per node), so
   those reads are local. Expert slabs stay interleaved (they are scheduled dynamically per
   token). `[NUMA] dense tensors (>=2 MB) bound by thread block: node0=14 cores node1=14 cores`
   in the log tells you it engaged.
   Cost: ~2 extra VMAs per dense tensor (a few thousand in total; `vm.max_map_count` is 65530).
3. **`COLI_THP=1`**: `madvise(MADV_HUGEPAGE)` on dense weights and expert slabs (2 MB pages for the TLB
   over 100+ GB of weights). Only has an effect where
   `/sys/kernel/mm/transparent_hugepage/enabled` is `madvise` or `always` (Alpine: check it).
4. Tests: `test_idot_extreme`, `test_numa_topo`, `test_numa_dense`; bench `bench_idot_tiers`.

Regression: the whole `make test-c` (about 320 test programs) passes, exit 0, built both with
`ARCH=native` (AVX-512 VNNI here) and `ARCH=skylake-avx512` (the new tier) on the VM.

musl: `colibri.c` compiles against musl's headers (Debian `musl-tools`, kernel headers via
`-idirafter`), and `test_idot_extreme` and `test_numa_topo` build and pass statically linked against
musl. Not done: a link against musl's OpenMP (libgomp is not in musl-tools), so a full Alpine build
is still for you to run (`apk add build-base`; Alpine's gcc ships libgomp).

## Run it on the 7820

```sh
git checkout perf/xeon-skylake-sp          # this branch, on top of dev
apk add build-base libgomp numactl hwloc   # musl: -fopenmp works with the gcc package
cd c && make colibri ARCH=native           # skylake-avx512 -> prints kernel "avx512bw"

# 1. correctness of the new tier on the real CPU (all must say ok)
make tests/test_idot tests/test_idot_extreme tests/test_idot_r16 tests/test_int_kernel_exact tests/test_numa_topo tests/test_numa_dense
for t in test_idot test_idot_extreme test_idot_r16 test_int_kernel_exact test_numa_topo test_numa_dense; do ./tests/$t; done

# 2. kernel throughput: avx2 vs avx512bw, one thread then the whole team
make tests/bench_idot_tiers ARCH=x86-64-v3      && mv tests/bench_idot_tiers /tmp/b_avx2
make tests/bench_idot_tiers ARCH=skylake-avx512 && mv tests/bench_idot_tiers /tmp/b_bw
for b in b_avx2 b_bw; do OMP_NUM_THREADS=1  /tmp/$b 1; done      # cache-resident: compute
for b in b_avx2 b_bw; do OMP_NUM_THREADS=28 OMP_PLACES=cores OMP_PROC_BIND=close /tmp/$b 2000; done  # DRAM: bandwidth

# 3. the engine: NUMA off / interleave / blocked
./tests/bench_hw_ab.sh /path/to/model         # prints tok/s per variant
```

`numactl -H` and `lscpu -e=CPU,NODE,CORE` first: confirm 2 nodes, and look at how CPUs are numbered.
A memory-bandwidth sanity check (STREAM, or `bench_idot_tiers 2000` with 28 threads): two sockets x
6 channels of 2666 should read ~200 GB/s in aggregate when every thread reads local memory,
roughly half of that when a thread block reads the other node.

## Bandwidth, not compute, is the thing to measure first on the 7820

`bench_expert_decode` (routed experts of one decode forward, weights streamed from DRAM) on a 4-core VM
ran at 2.5-3x its own read floor: compute-bound already at 4 threads. With 28 cores and 12 channels the
read floor is ~6x lower relative to the compute, so the kernels' instruction count matters *more* on
the 7820 than it did here. That is the case for the AVX-512BW tier. It is also why a VM benchmark can
not settle it: run `gcc -O3 -march=skylake-avx512 -fopenmp tests/bench_expert_decode.c -lm` against the
`-march=x86-64-v3` build on the real box, with `OMP_NUM_THREADS=28` and then 56.

## Ideas not done (in the order I would try them)

- **Expert slabs by node.** Decode computes (expert, row-chunk) tasks with `schedule(dynamic,1)`
  from all threads, so each token reads experts half remote. A two-level scheduler (an expert's
  slab bound to node `slot % nodes`, its chunks handed to that node's threads first) would
  localise those too: the largest remaining NUMA gain, and the most invasive change.
- Replicate the dense trunk per node (192 GB has the room; threads pick their node's copy):
  trades memory for always-local reads, without relying on the row split matching.
- `-mprefer-vector-width=256` for the compiler-vectorised loops (the licence issue above),
  keeping the hand-written 512-bit kernels.
- Port `i8r16`-style biased-uint8 expert kernels (`ggml_quants.h`, `expert_ffn.h`) to the
  sign-trick 512-bit form, as was done for the dense r16 kernel here.
- SNC / sub-NUMA clustering is a BIOS option on this platform: with it off you have 2 nodes
  (what the code assumes); with it on, 4, and the code handles N nodes but was never tried.
